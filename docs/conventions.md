# 协作与文档规范

## 格式与职责

- 文档默认使用中文、UTF-8、Markdown；文件名和目录名使用小写英文及连字符，产品名称保留官方写法。
- 时间使用 `YYYY-MM-DD HH:mm +08:00`；仅需日期时使用 `YYYY-MM-DD`。来自其他时区的证据保留原时区并注明换算。
- 每个项目指定一位负责人，其他成员可协助执行和确认。成员可以使用稳定代号，代号与职责在项目说明中登记。
- 项目负责人协调资料完整性；执行人对实际操作负责；记录人对来源和转录负责；人工确认人对测试结论及风险判断负责。可以兼任，当前不强制另一位同事审核。
- 文档正文应区分事实、假设、待确认事项。空缺统一写“待补充”，未知事实写“待确认”，未分配人员写“待指定”。

## 命名与编号

批次目录采用 `YYYY-MM-DD-topic`，例如命名形式 `YYYY-MM-DD-login-regression`。相同日期与主题冲突时追加 `-02` 等序号；创建后不随结束日期重命名。

| 对象 | 编号格式 | 唯一范围 |
| --- | --- | --- |
| 需求 | REQ-001 | 当前项目、当前批次 |
| 用例 | TC-001 | 当前项目、当前批次 |
| 执行记录 | RUN-001 | 当前项目、当前批次 |
| 缺陷 | BUG-001 | 当前项目、当前批次 |
| 可复用回归用例 | REG-001 | 当前项目 |

数字从 001 递增，超过 999 时继续增长；各类单独编号。废弃编号保留并说明原因，不再分配给其他对象。多人新增记录前检查已有最大编号，发生冲突时调整尚未被引用的新记录并更新其引用。

同批次引用包含编号和相对文档链接；跨批次引用同时写明项目、完整批次目录名、编号及链接。正式记录标题使用实际编号，替换模板里的“待分配”。需求和用例使用 `r1`、`r2` 等修订号；执行记录固定引用执行时的修订号，不能跟随正文变更而自动更新。

## 修改与版本

需求、用例的重要变更在所在文档变更表中写明编号、旧/新修订号、内容、原因、日期和记录人。能使用 Git 提交定位历史时同时记录提交标识；尚未提交时，在变更说明中保留原步骤、原预期等必要差异，使执行当时的内容仍可还原。

执行记录和人工确认历史以追加为主。发现误录时增加更正说明，标明原记录、正确内容及依据，不静默覆盖历史。已经归档的批次需要补充时，写明补充原因，不改变当时的测试范围和结论事实。

## 三人协作

1. 开始编辑前查看本地改动。已配置远端时先获取更新并按团队方式同步；未配置远端时跳过同步，不自行添加远端或推送。
2. 在批次索引明确负责人和参与成员；同时编辑同一份文档前协调负责段落或编号，避免互相覆盖。
3. 一次提交围绕一个主题，建议提交说明使用 `docs(项目): 动作与主题`，公共规范使用 `docs(shared): 动作与主题`。
4. 提交前检查链接、编号、结果证据及脱敏情况。Agent 是否提交由当前任务授权决定。
5. 冲突涉及测试事实、执行结果或结论时，由相关记录人确认后合并；不得只为消除冲突而选择某一侧。

## 文档生效与引用

草稿、待确认内容需要明确标注。公共规则变更记录在本文件末尾，并检查三个项目规则是否兼容。最终测试结论遵守[人工确认规则](results-and-review.md)。外部需求或缺陷链接可以作为来源，仓库仍维护本批次所需摘要、版本依据和追溯关系。
