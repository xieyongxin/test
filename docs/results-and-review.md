# 结果、证据与人工确认

## 执行状态

| 状态 | 使用条件 | 最低记录要求 |
| --- | --- | --- |
| 未执行 | 尚未进行测试 | 用例、原因或后续安排；不得填成已通过 |
| 通过 | 真实执行符合预期，且有可追溯证据 | 实际结果、执行者、时间、环境、构建、用例修订和证据 |
| 失败 | 已执行且实际结果与预期不符 | 差异、证据、缺陷链接或尚未登记原因 |
| 阻塞 | 前提或环境问题使测试无法完成 | 阻塞现象、原因、解除条件及已有证据（如有） |
| 不适用 | 当前范围/环境下该用例不应执行 | 具体原因、范围依据和人工确认人；确认前不作为已排除项 |

证据可以是脱敏截图、日志、工具输出、接口响应或详细且可追溯的人工观察记录，不强制每个结果都配截图。人工观察应注明观察者、时间、操作、观察到的事实和对应检查点。不能只写“正常”“已通过”作为证据。外部证据需要稳定可访问的位置及版本标识。

“待确认”是资料核实状态，不是第六种执行结果。遇到来源声称通过但证据缺失的旧资料，保留其原始声称，标注“待确认”；当前批次汇总不得将其计为已验证通过。

## 统计口径

- 报告明确统计时间、目标构建、环境和用例修订；多个目标分别统计，不能混用不同版本的结果。
- 同一用例在相同目标下以截至统计时间的最新有效 RUN 作为当前结果，历史执行仍保留。重试次数与用例数分开统计。
- 当前有效通过、失败、阻塞、未执行、已确认不适用合计应等于选定用例数。没有符合目标的有效执行记录时按未执行统计；证据待确认的条目额外列出，不计为通过。
- 执行完成率 =（通过 + 失败）/（选定用例数 − 已确认不适用）；通过率 = 通过 /（通过 + 失败）。分母为零时写“不适用”，不得写 100%。
- 尚未执行时统计字段写“待统计”，不得把模板中的空值当成零缺陷或零风险结论。存在有效记录后再计算实际数字。

## 缺陷状态与严重程度

缺陷状态使用：待确认、已确认、处理中、待复测、已关闭、重新打开、不予修复。关闭须关联有效复测证据；“不予修复”须记录原因及人工决定人，重复问题注明原缺陷链接，不等于测试通过。

严重程度使用 S1（系统不可用、数据损坏或重大安全风险）、S2（主要功能失效）、S3（一般功能异常）、S4（轻微体验或文案问题）。严重程度描述影响，修复优先级由项目成员依据实际情况协调，不与用例优先级混为一谈。

## 人工确认

报告分开记录“结论建议”和“人工确认记录”。确认记录包括确认人、确认时间、确认结论、适用构建/环境、剩余风险及其处理决定。Agent 可整理建议，人工确认栏必须保留为待确认，除非用户明确提供真实确认事实和身份；代录时注明来源。

结论建议可使用“满足本次范围的验收要求”“存在限制，待人工决定”“不满足本次范围的验收要求”或“证据不足，暂不能判断”，并陈述依据。人工确认不是单纯填写一个状态；不得仅因没有发现缺陷而判断可以发布。

确认后出现影响范围的变化时，追加影响说明和新确认记录，保留原确认的适用范围与历史。当前不强制双人审批，但应能识别实际确认人。
