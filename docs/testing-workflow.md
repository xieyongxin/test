# 测试流程

## 1. 建立批次

复制[批次模板](../templates/batch/README.md)所在的整个目录到项目 `batches/`，填写索引并更新项目批次列表。类型可选需求测试、版本回归、专项测试或组合。批次状态使用：准备中、执行中、待人工确认、已归档、已取消；取消时保留已有记录和原因。

每批至少维护索引、用例和执行记录。需求分析、计划、缺陷记录、报告按需使用，索引标明“适用”或“不适用”及原因；暂未填写写“待补充”，不能把缺少资料写成不适用。需要给出最终测试结论的批次必须使用报告。

## 2. 明确需求与范围

收集原始文件或链接，记录来源、版本、验收标准和疑问。为本批次需求分配 REQ 编号；版本回归可记录本次回归目标及其依据。计划说明范围、排除项、资源、风险和完成条件。轻量批次可将计划简述写在索引中。

## 3. 设计用例

为用例分配 TC 编号，关联需求和修订号，写清前置条件、数据、步骤、预期结果和优先级。需求分析不单独成文时，在用例中说明来源文件/章节及版本。优先级使用 P0（核心链路或重大损失风险）、P1（主要功能）、P2（一般边界或低影响场景）。

使用回归库时，将本次选定用例复制成批次用例，记录来源 REG 编号和修订号，形成当次快照；之后回归库更新不自动改变本批次。

## 4. 执行与登记

实际执行后按用例新增 RUN 记录。每条记录对应一个用例修订、一个环境和一个构建；多轮执行分别编号。记录实际表现和证据，不将预期结果复制为实际结果。未执行项可在覆盖表中登记，实际测试时间留为“尚未执行”。

失败时登记或关联缺陷；阻塞时说明前提、责任方（已知时）、解除条件和后续安排。证据按[附件规则](attachments-and-security.md)脱敏后登记。阶段汇总遵守[结果规则](results-and-review.md)。

## 5. 修复、变更与复测

缺陷修复后，在新构建上创建新的 RUN 记录，引用原失败记录及缺陷，不覆盖原结果。更新缺陷状态和复测关联。需求或用例变化时提升修订号，写明影响范围，旧结果只证明旧修订的执行情况，修改后的用例需要重新评估覆盖和复测。

## 6. 总结与归档

核对用例覆盖、最新有效执行状态、未解决缺陷、未覆盖项和风险。需要测试结论时生成报告并置为待人工确认；人工确认后保留确认人、时间及适用构建。结论不能替代发布审批。

不需要正式报告的批次在索引说明原因，并由批次负责人记录结束情况及归档日期。取消的批次记录取消原因，无需伪造测试完成。归档前检查链接、敏感信息、附件和统计；更新项目批次列表。可复用知识和用例经核实后沉淀到项目知识区和回归库，保留来源链接。
